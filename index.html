Approach

How I take an idea to production

I run operations work like a product: put a number on the friction, reuse what already exists, build the guardrails in, and stay with it until people use it without being asked.

1

Follow the hours

Sit with the team, count the steps and the people waiting on them, and pick the problem that has a number attached.

Example: 400+ staff couldn't see how their time was planned across clients, so I led a company-wide resourcing tool →
2

Assemble before you build

Connectors, skills and templates first. Code only fills the gaps, so there's less to break and less to maintain.

Example: new-client onboarding automated by chaining 20 AI skills together, with no new app to maintain →
3

Make it safe to fail

Test modes, allow-lists and a human sign-off before anything reaches a client, a CRM or a colleague's inbox.

Example: AI suggests which clients to survey, and account leads approve every name before anyone is contacted →
4

Earn the adoption

Focus groups, a public feedback board and release notes. It isn't finished until it's part of how people work.

Example: 140 of 158 user requests shipped in a resourcing tool now used by every leader →
Principles

Things I've learned about operations & automation

Context and memory make automation smart.Generic automation gives generic output. Every skill I build reads the same shared client context (goals, structure, contacts, what was promised in the pitch), so nobody has to explain the account again each time and the drafts read like they came from someone who knows it.
Adoption is the real launch.A tool nobody opens has saved no one any time. The rollouts that stuck had users shaping every release, plus training, guides and self-service help so people knew the best practices and could answer their own questions.
Let AI draft, let people decide.AI writes the handover, builds the contact list and suggests the team. A person approves the step that can't be undone, which is why teams trust it with real clients.
Meet people where they already are.Another dashboard is just another bookmark. The goal is to put the right information in the tools people already live in, like a Slack message on the day it matters, so most of what I build ends in a nudge, not a link.
Document so it outlives the builder.Every project gets a runbook: how it works, where the data comes from, what to do when it breaks and what's next. Anyone can pick up the work or fix an issue without waiting on me.
Security & privacy

Safe by design, not as an afterthought

Most of what I build touches client data, calendars or people's inboxes, so security and privacy are designed in from the first sketch and signed off before anything goes live.

Threat-modelled and signed off

Production builds are threat-modelled with SecOps, with data protection review wherever personal data is involved.

Consent and least privilege

Per-person OAuth consent instead of blanket access, and every service account scoped to the one job it does.

No secrets in code

Credentials live in Secret Manager, tokens are encrypted, and deployments run keyless through Workload Identity Federation.

Only the data that's needed

Sensitive content is processed in memory and never stored, logs are redacted, and every view is filtered to what that person may see.

Humans at the irreversible step

Test modes, allow-lists and approvals before anything writes to a CRM or reaches a client or colleague.

Audited and governed

Every run logs what it did and why, and AI skills pass governance review before anyone can use them.
