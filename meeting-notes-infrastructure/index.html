The problem

Notes lived everywhere, and nowhere

The agency runs hundreds of client meetings every day on Google Meet. Before this project, the notes from those meetings lived wherever the person taking them happened to put them: a private Notion page, a personal Google Doc, a Gemini note sitting in one person's Drive, or nowhere at all.

Before

Private Notion page Personal Google Doc Gemini note in one person's Drive Notebook Nowhere

Hundreds of client calls a day. Every account team keeps notes its own way, so there is no shared record, no way to see how a client relationship is trending, and nothing to read before the next call.

After

Captured automatically Filtered for sensitivity One client database per region Sentiment, risk and expansion signals Action items with owners

Consent once. After every client meeting, the Gemini or Notion AI note is checked, analysed and filed against the right client in Notion, with no one lifting a finger.

That fragmentation had real costs. Account leads walked into calls without the context of the last three. Nobody could see whether a client relationship was warming up or cooling down until it showed up in revenue. Action items agreed on a call depended on someone remembering to write them down. And because every team had its own habits, there was no single place leadership could look to understand what clients were actually saying.

The obvious fix (capture every meeting centrally) runs straight into the reasons nobody had done it. An org-wide system touches every employee's calendar and the content of their conversations, so it has to answer hard questions about privacy, GDPR, client confidentiality and security before it can process a single meeting. A previous attempt in early 2026 stalled on exactly those issues, plus API readiness and routing complexity.

The brief: capture client meeting notes automatically, keep anything sensitive out, file the rest against the right client, and add a signal layer (sentiment, risk, expansion, actions) that account teams can use. Do it in a way SecOps and the Data Protection Officer will sign off.

The solution

A pipeline that decides before it reads

A scheduled pipeline on Google Cloud that, every 30 minutes through the working day, looks at the meetings each consenting participant attended, decides from calendar metadata alone whether the meeting is in scope, and only then reads the AI-generated note. Claude checks the note for sensitive content and extracts a structured analysis. Cleared meetings are written to a regional Notion database as a record with a summary, action items with owners, and a set of client-health scores. The transcript itself is never stored.

Consent, not delegation

Each person grants read-only access to their own account through a branded self-service link. There is no service account and no domain-wide delegation, so the system can never see anyone who has not opted in.

Decide on metadata first

Five of the eight rules run before a single word of the meeting is read. Most out-of-scope meetings (wrong client, internal 1:1, HR, private events) are rejected without their content ever leaving Google.

Fail closed, and say why

Every exclusion is logged with a machine-readable reason. When the system is unsure (no calendar event, unreadable note, unknown client) it leaves the meeting out rather than guessing, and the log becomes the tuning loop.

How it works

Eight rules, every run

Every scheduled run applies the same eight rules, in order. Each exclusion is logged with a machine-readable reason.

The rules, in order
1
Calendar matchMeet code → Calendar event

The Meet conference record is joined to its Google Calendar event by meeting code. No event means no metadata to judge, so the meeting is excluded.

2
Gate 1, the pre-filterTitle block-list + visibility

The event title is checked against a block-list (1:1, PIP, HR, performance review, salary, legal, M&A, board meeting, confidential), and events marked private or confidential are skipped. Matching is word-boundary based, so "HR" never matches "CHRIS".

3
Client scopeAttendee email domains

For a meeting with external attendees, at least one must come from an approved client's confirmed invite domain. Domains are confirmed against real calendar invites, never taken from a website or a CRM field.

4
Title client checkInternal meetings only

An internal meeting has no client domain to check, so its title must name an approved client by name or the team's abbreviation. Before this rule existed, the pipeline had to read a note and pay for a model call just to learn the meeting was never eligible.

5
Settle delay15 minutes

Gemini takes a few minutes to finish writing its note, so any meeting that ended less than 15 minutes ago waits for the next run.

Nothing above this line reads a word of the meeting
6
Gate 2, sensitivityDocs API read + Claude

The note is read through the Google Docs API and sent to Claude, which returns a structured result: whether the content is sensitive, plus summary points, action items, attendee sides and sentiment counts. Anything flagged is held for review and never written to Notion.

7
Dedupe and backstopGemini wins over Notion

The same meeting can arrive as a Gemini note and a Notion AI note. One page per meeting is kept (Gemini wins), and internal meetings with no client are caught again here in case rule 4 is switched off.

8
ClearedWritten to Notion

A record is written to the client's regional Notion database with a link back to the original note. Derived fields only, never the transcript.

Architecture

Three paths, three trust boundaries

The system splits into three independent paths. Labels A, B and C are separate workflows, not one sequence.

AConsent

One time, per person

A public Cloud Run service, fronted by Identity-Aware Proxy, runs the Google OAuth flow (and optionally Notion's). The resulting token is encrypted and stored in Firestore alongside a consent record.

BCapture

Every 30 minutes

Cloud Scheduler triggers a Cloud Run Job with an OIDC identity. The job has no HTTP surface at all. It calls Google Workspace as each consenting participant, sends note content to Claude, and writes derived fields to Notion. A Firestore collection holds the audit and dedupe trail, metadata only.

CDeploy

On merge to main

GitHub Actions authenticates to Google Cloud through Workload Identity Federation, with no stored keys, and Terraform provisions every resource inside the project boundary from locked, versioned state.

Technical detail

Under the hood

Capture: polling, by design

Google offers a webhook through the Workspace Events API, but it needs a public endpoint and Pub/Sub. The pipeline polls recent conference records through the Meet API instead. Polling uses the same read-only access, has no inbound surface to attack, and stayed inside the original security approval. The poll and webhook adapters hand the pipeline the same event shape, so switching later is a drop-in.

Gate 2: Claude with structured output

A single Claude call (Claude Opus 5.5, with Sonnet 5.5 as fallback) returns a typed MeetingAnalysis object, validated by Pydantic. It carries the sensitivity decision (sensitive_content_found, hold_for_review, a reason), the meeting type, client name, summary points, action items with owners, attendee sides, and a set of counts: positive and negative indicators, courtesy signals, contribution points, risk signals and expansion signals.

The model reports counts; code does the arithmetic

Running the same note twice showed the raw counts drift by about 20% while the ratios held steady at 0.29. So the model is never asked for a score, only for the counts the score is computed from.

The prompt is plain text in the repository

Tuning what counts as sensitive is a one-line edit through GitHub's web editor, deployed in about five minutes.

Scoring: a documented, deterministic formula

# scoring.py · Weighted Sentiment Score
polarity = (pos − neg) ÷ (pos + neg + 2)
sentiment = 5 + 5 × polarity
engagement = min(client_engagement ÷ 2, 1) × 10
base = min(sentiment × 0.7 + engagement × 0.3, 9)
score = base − min(2 × risk, 6) + (1 if expansion)
# clamped to 1–10

Capped at 9 on purpose. A meeting can only reach 10 if it is healthy, engaged and carries a growth signal, which is what "ideal" means for an account.

Binary expansion bonus. A chatty planning call cannot outrank a healthy relationship.

Smoothed polarity. The +2 in the denominator stops the score depending on how long the meeting ran.

Privacy and security controls

  • No transcript storageNote content is held in memory for the Gate 2 call and then discarded. It is never written to disk, logs, Firestore or Notion.
  • Separation of dutiesThe service that stores tokens and the service that uses them hold separate permissions, so neither can do both.
  • Redacted logs that still diagnoseException messages are stripped, but the HTTP status, the provider's reason code and the file and line in our code are kept. All three are fixed vocabulary, so they cannot carry meeting content.
  • Scope you can auditEvery run logs a scope_hash of the participant and client boundary in force, so any historical run can be tied to the exact rules it ran under.
  • Approved clients cannot be admitted by accidentTitle matching only ever compares against the approved list, and a client's name is never used as a security input: only a confirmed domain is.
  • Formal sign-offThreat-modelled and approved with SecOps, with a major-change amendment for the client pilot, reviewed with the DPO, and provisioned with the Platform team.

A second note source: Notion AI Meeting Notes

Many people take notes in Notion rather than Gemini. Notion AI recordings happen across the agency every day, so the pipeline now reads them too, through a per-person Notion OAuth connection set up in the same consent flow. Both sources pass through the same gates. A cross-source dedupe key (a hash of the calendar event's iCalUID and start time) ensures one page per meeting, and when a team starts a note inside an existing Notion template row, the pipeline fills that row rather than creating a duplicate.

Engineering practice

Pure logic separated from I/O. Every adapter (Meet, Calendar, Docs, Claude, Notion) has a fake mode backed by fixtures, so the whole pipeline ran end to end offline before a single live credential existed.

Automated tests cover each gate, the scoring formula, consent decisions, token storage, dedupe and the retry rules.

Infrastructure as code. Every resource is in Terraform and deployed through GitHub Actions, following the Platform team's house pattern.

Self-healing reads. A failed note read is deferred and retried (six attempts, or two for a permission error, which is permanent), and a replay tool reopens read failures without being able to reopen any other kind of exclusion.

Key impact

What changed

Automatic

From scattered notes to every in-scope client meeting filed, with no manual work

Account teams get a summary, owned action items and a link to the full note in one place, organized by client and region.

Opt-in

Adoption without a mandate

People opted in through a two-click link, with no install, no training and no IT ticket.

Private

Privacy that holds up to review

Most meetings the system sees are excluded, almost all of them before their content is read, and nothing sensitive reaches Notion.

New

A signal layer for account health

Client meetings now carry comparable sentiment, engagement, risk and expansion scores, the foundation for spotting at-risk accounts before they show up in revenue.

Reusable

A pattern for the next team

The consent service, token handling, Terraform and CI setup, and the lessons on PKCE, IAM and Workload Identity limits are written up as a playbook for the next team building on Google Cloud.
